# Manage networking — generic sample

Read existing People records and the person's conversation toggles before searching or updating. Match by verified professional identity/profile rather than name alone. Use the user's supplied connection preferences; this generic sample contains no school, nationality or personal targeting criteria.

For discovery, return a small set of sourced identities, current role/team where verified, evidence for the requested connection, useful question and next step. Keep referral willingness unknown unless explicitly established. Limited public access is a limitation, not permission to guess. Reuse the existing person record and contact/profile field.

For a refresh, distinguish checked facts from older user notes. Record source/check date, preserve relationship stage and existing company associations, and leave unverified details explicit. Refreshing a profile does not mean outreach occurred.

For conversation logging, append a native dated toggle in the existing People page using the connector's supported format. Include actual substance, agreed follow-up/date and source/context where appropriate. Preserve earlier toggles. If the same conversation was already logged, update/correct that entry instead of duplicating it. Use [the person template](../../templates/person-page.md); do not create an interaction database.

Keep the current next action/date in People properties for sorting and its historical context in the corresponding toggle. A draft stays Draft; mark sent/replied/met only from evidence or the user's explicit account. This skill does not authorize sending messages, making introductions or requesting referrals on the user's behalf.
