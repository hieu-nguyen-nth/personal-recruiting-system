# Supporting artifacts: evidence, wording and workflow state

These inputs live in a private recruiting workspace, not extra Notion databases. Start with existing evidence; story and bullet banks can be sections of one file until splitting is useful. The only completed candidate artifacts in this repository are [invented teaching fixtures](../examples/fictional-case/inputs/candidate-evidence.md). Copy the [blank pack](../templates/supporting-artifacts.md) outside the checkout before adding real facts.

| Artifact | Purpose and minimum contents | Primary reader / authority |
|---|---|---|
| Master resume | Verified chronology, role titles/dates, education and broad accomplishments | Evaluation, tailoring, QA; chronology/credential reference |
| Story bank | Stable story ID, context, personal role, actions, outcome, measurement definition, scope, evidence and limits | Tailoring/QA; underlying achievement evidence |
| Bullet bank | Alternative phrasings, linked story ID, proposed/approved state and version | Tailoring; wording only, never independent proof |
| Skills inventory | Tool/method, actual proficiency, context and story/source demonstrating use | Tailoring/QA; distinguish learning, prototype and production |
| Recruiting playbook | User goals, target scope, fit criteria, constraints and rules for effort | Evaluation/coordinator; private preferences, not evidence that a fact occurred |
| Exact JD and company brief | Versioned role requirements plus an independent executive company brief, six-section profile, dated findings and uncertainties | Evaluation, research, tailoring and QA; separate official requirements from inference |
| Template and application outputs | Original layout, role-specific copies, exact text/export versions and associated QA | Optional document tools and human review; exports are derived artifacts |
| Job-page checkpoint | Last step, requested stop, source versions, exact current/reviewed draft, open questions and next owner | Coordinator/new chat; continuation state, not a new source of career facts |

## Example: how evidence travels

In the [synthetic pack](../examples/fictional-case/inputs/candidate-evidence.md), EX-E01 establishes observations, assisted contribution and a one-desk pilot. The [proposal](../examples/fictional-case/outputs/tailoring-proposal.md) uses those facts for the observation requirement. [QA](../examples/fictional-case/outputs/qa-review.md) returns to EX-E01 when a later reviewer adds an unsupported retention claim; it does not trust the new bullet because it sounds persuasive.

A blank story entry should preserve these distinctions:

```text
Story ID / version:
Context and time period:
Personal responsibility versus team/supervisor responsibility:
Actions, decisions and tradeoffs:
Outcome / units / baseline / sample / time window:
Evidence location and measurement definition:
Limits: unmeasured outcomes, pilot scope, attribution, unresolved facts:
```

## General positioning example

A candidate with equipment-desk observation experience may have strong **functional fit** for discovery work but only partial **industry fit** for museum software. That supports emphasizing observation method while learning the domain; it does not justify claiming museum expertise. A production-engineering role can remain a poor fit despite the same employer and appealing product.

This is a reusable distinction, not a personal targeting strategy. A private playbook may weight dimensions differently; it cannot alter the facts in a story or supply a missing qualification.

## Source precedence and refresh

Use explicit current user corrections and authoritative evidence before older resume phrasing or derived bullets. When sources conflict without a confirmed correction, retain the conflict rather than choosing a stronger number. Record a canonical location and version/date per artifact. A connected snapshot is a dated reference, not another editable master.

When the JD or source evidence changes, refresh relevant mappings and recheck affected claims. When only phrasing changes, review the new draft/version. Never assume a different chat or cloud runtime can read a local file. Record the versions QA actually used, and keep private evidence out of shared outputs and repository history.
