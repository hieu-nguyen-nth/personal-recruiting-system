# Create and prove the schedule

Choose the execution environment explicitly. **Local Codex** is suitable when the computer can remain awake with Codex running; use a heartbeat attached to a dedicated recruiting-operations chat, separate from system-maintenance conversations. **Cloud** is needed if the workflow must run while the computer is off. Check the exact runtime's connectors and scheduling rather than assuming access transfers between them. Official guidance: [scheduled tasks](https://learn.chatgpt.com/docs/automations) and [setup walkthrough](https://developers.openai.com/training/walkthroughs/scheduled-tasks).

1. Connect the job source and Notion in the selected execution chat, and make the private methods and candidate reference readable there. Test one full JD read and a marked Notion test-page write interactively. Record actual errors and approval requirements.
2. From that chat, ask the scheduler to **create one one-time task** using [the smoke-test prompt](../prompts/scheduled-smoke-test.md), with a concrete future time and time zone. Inspect the returned schedule card/task entry. Record its actual URL/identifier and displayed run time in the private setup note.
3. Let that actual task run: keep the computer awake for local execution; test with it asleep only for cloud execution. Inspect scheduler history and the specific Notion writeback. Interactive success or task creation is insufficient proof. An attached heartbeat may wait until the current chat is idle.
4. If it succeeds, create **one recurring task** using [the short recurring prompt](../prompts/daily-scan.md) linked to the [maintained scan procedure](scan-procedure.md) and your chosen cadence/time zone. Alternatively, create recurrence with a guard that runs the smoke checks first and stops dependent work on failure. Record the actual ID/link and configured time separately from an observed next run. Do not invent a URL or next-run timestamp the scheduler did not return. Check the first actual execution and ensure the one-time test is completed/inactive.
5. In Codex Automations or the selected scheduler, inspect run details and edit, pause or delete the task. Keep only the intended recurrence. Recheck access after changing connectors or private references.

If the selected runtime cannot execute the required reads/writes, name the missing capability and leave that step incomplete. Change runtime only with the user's agreement. A reminder to do the work is not an automated scan. Add custom infrastructure only after the limitation and tradeoff are understood.
