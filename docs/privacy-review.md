# Sharing review

This repository contains general methods, blank templates and an entirely invented teaching case. Private candidate methods, scoring weights, real evidence, account bindings and individual targeting strategy are excluded. The case is authored from scratch, not derived by changing names in a real resume. Its dates/numbers, professional community, organizations and source excerpts are synthetic. Reserved example.invalid addresses do not identify real people or publications.

## Before every upload

1. Enumerate every file in the proposed tree, including unchanged files, images, hidden files and generated assets. Stage an explicit allowlist; keep private work outside this checkout. Ignore rules are a secondary safeguard, not a publication boundary.
2. Read the complete proposed content. Check for legal names, email/phone/address details, schools/nationality/background, real employers/contacts, application histories, actual strategy, resume claims, internal project details, credentials, local paths and document/database/task IDs. Inspect diagram text and metadata too.
3. Review new demonstrations separately against private source material. Look for distinctive copied phrases, project narratives, metrics and combinations that could reconstruct an achievement, even after names are changed. Generic workflow terms are expected; unique achievement overlap requires rewriting or removal. Keep that comparison and its findings private.
4. Search for secrets, private URLs/identifiers, file paths and accidental copied text. Automated checks complement semantic review; no string scanner proves complete anonymity or absence of paraphrase.
5. Inspect the staged diff, intended commit author/committer and reachable history before uploading. An innocuous new commit does not remove an older disclosure. Confirm there are no unexpected files or binary exports.
6. After upload, read back the changed content and confirm the remote commit/tree matches the reviewed content. Preserve repository visibility unless the user explicitly changes it.

## Demonstration review rules

Do not present synthetic sources as real citations, hypothetical conversations as sent messages, reference answers as model-run transcripts, or simulated digests as scheduled execution. Keep candidate facts separate from general fit principles. A public example can explain industry versus functional fit without exposing an individual's actual preferences or weights.

A maintainer-reported integration summary can describe checked capabilities without reproducing employers, account identifiers, raw records or logs. Explain the evidence limit; see [capabilities](capabilities-and-validation.md). Optional document/PDF stages must not be described as verified when no exact file was checked.

## Account-level limits

Sanitized contents do not make repository ownership or activity anonymous. Account name, access permissions and hosting metadata remain properties of the service. Use neutral commit attribution for this reusable kit and avoid embedding account/profile details in its content. A private repository still requires the same content review before sharing.
